# Contributing to cascade-knowledge

This repository is data with a strict contract. Everything here is designed so
that correctness is checkable by a machine, not by trust. The contract below is
the same one a future in-app contribution flow will target.

> Community contribution mechanics (an intake queue, pooling/k-anonymity, and an
> agent-assisted drafting flow) arrive in a later version. For now, contributions
> are ordinary pull requests reviewed against this contract.

## The row contract

Every row is one line of JSON in a `data/<family>.jsonl` file and must validate
against that family's schema in `schema/`. The canonical shape:

```json
{
  "subject": { "system": "<code system>", "code": "<optional>", "display": "<label>" },
  "predicate": "<family predicate>",
  "object": { "system": "<code system>", "code": "<optional>", "display": "<label>" },
  "provenance": {
    "source": "<allowlisted source>",
    "sourceVersion": "<pinned release>",
    "method": "curated | derived",
    "evidenceTier": "candidate | established",
    "citation": "<resolvable https URL>",
    "addedDate": "YYYY-MM-DD",
    "reviewedDate": "YYYY-MM-DD"
  }
}
```

Rules:

- **Provenance is required on every row.** No row without a source, a citation,
  a method, a tier, and dates.
- **Evidence tiers are conservative.** New or community rows land as `candidate`.
  Promotion to `established` requires maintainer ratification. Applications
  choose whether to consume `candidate` rows.
- **Dates are constants, never wall-clock.** A build must reproduce the same
  bytes. Use the build date constant, not `new Date()`.
- **Free-text subjects** (lay synonyms) use system `text` and omit `code`.

## The license rules (the wall)

- Every row's `source` must be on the open allowlist in `sources/allowlist.json`,
  and every `subject.system` / `object.system` must be an open code system.
- **Walled sources are structurally rejected.** A SNOMED CT, full-UMLS, or ATC
  identifier will fail validation and can never be committed. Mappings derived
  from those sources belong in `overlay/` as a local build, never in `data/`.
- Adding a new source means: verify its license permits redistribution, record
  the verdict and a canonical URL in `SOURCES.md` and `sources/allowlist.json`,
  and add any required attribution notice to `LICENSE-NOTICES.md`. A murky
  verdict is a documented stub plus a question, never committed rows.

## Determinism and regeneration

Bulk families are regenerated by deterministic scripts under `scripts/build/`,
each pinning its source release in `sources/SOURCE_VERSIONS.json`. Do not
hand-edit generated `data/` files; change the pipeline or the committed seed and
rebuild. Curated rows migrated from seeds live in `sources/checkup-curation/`.

## CI gates (all must pass)

```bash
node --test                                                   # unit + integration
node scripts/gen-schemas.mjs && git diff --exit-code schema/  # schemas match generator
node scripts/validate-all.mjs                                 # schema + allowlist wall + determinism
node scripts/validate/validate-code-existence.mjs --sample 12 # codes exist in canonical APIs
```

- **schema**: every row conforms to its family schema.
- **allowlist**: every row's source and code systems are open (the wall proof).
- **determinism / integrity**: committed files match the build manifest; the
  CI-rebuildable pipelines rebuild byte-for-byte.
- **code-existence**: a throttled sample of codes is confirmed against RxNav
  (RxNorm), and the NLM Clinical Table Search Service (LOINC, ICD-10-CM).

## What does not belong here

Protocol vocabulary changes (those stay in the `spec/` repo), application code,
and anything derived from a license-walled source. Data-layer rows only.
